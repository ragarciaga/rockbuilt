# Evals reference

Loaded by the verify skill for Gate C. A unit test compares against one fixed value; an eval
judges an output that can differ on every run because an LLM sits somewhere in the path. The eval
gives a score and a reason, and a threshold on the score becomes a regression gate.

## When evals apply

- CLAUDE.md `Project type` includes `ai`, or a criterion is tagged `[eval]`, or design.md marks a
  node as `llm`.
- Not for deterministic code paths (use unit tests) and not for non-generative `ai-model` nodes
  with exact outputs (use unit or integration tests with fixtures).

## Anatomy and vocabulary

| Piece | Meaning |
|---|---|
| Dataset | 20 to 50 real cases with ground truth |
| Target | The system under test: one LLM call, a workflow, an agent, or a hybrid |
| Grader | Logic that scores the target's output against the ground truth |
| Score + reason | 0 to 1 per case, plus a one-line explanation |
| Task / trial | A case / one execution of it. Run k trials per task for non-deterministic targets |
| Transcript | Everything that happened in a trial: model outputs, tool calls, intermediate state |
| Outcome | The final answer or end state. Grade this, not the path |

Tracing: for agents, enable tracing at 100% sampling while building evals, so every failing case
has a transcript to read.

## Dataset

Format: JSONL (preferred) or CSV, at `evals/datasets/<name>.jsonl`, committed.

```jsonl
{"id":"t001","input":"El audio se corta en llamadas largas","expected":{"topic":"audio-calidad","actionable":true},"tags":["positive","audio"]}
{"id":"t002","input":"Gracias, todo funciona","expected":{"topic":"ruido","actionable":false},"tags":["negative"]}
```

CSV equivalent: `id,input,expected,tags` with `expected` as a JSON string and `tags` separated
by `|`.

Rules:
- Real cases (production logs, support tickets, user examples). Ground truth is labelled by a
  human, never generated by the model under test.
- Balanced: cases where the behavior should trigger and cases where it should not, and coverage
  of each category in proportion to how much it matters (not only how often it appears).
- Tag every case so scores can be broken down by tag.
- Every production failure becomes a new case (with its id and source date) before it is fixed.

## Graders, in order of preference

1. **Code** (deterministic, cheap, objective): exact or normalized match, set overlap, pairwise
   co-grouping, schema validation, "tool X was called with argument Y" read from the transcript,
   forbidden content regex. Anything measurable by code is measured by code.
2. **LLM as judge** (flexible, costs tokens, non-deterministic): only for what code cannot
   measure (tone, faithfulness to a source, completeness). Must be calibrated (below).
3. **Human review**: the most reliable and the most expensive. Used to label ground truth, to
   calibrate the judge, and to review transcripts. Not a per-run grader.

Combine them: code graders gate, the judge adds nuance, humans keep both honest.

### Pseudocode

```
for case in dataset:
  for trial in 1..k:
    output, transcript = run_target(case.input)
    score, reason = grade(output, case.expected)      # 0..1
    record(case.id, trial, score, reason, transcript_ref)
aggregate: mean score, pass rate (score >= case_pass), pass^k per case, breakdown by tag
exit 1 if aggregate < threshold
```

### Minimal runnable example (no framework)

`evals/topic.eval.ts`, run with `npx tsx evals/topic.eval.ts` (or `node --experimental-strip-types`
on Node 22.6+). It uses only `node:fs`. Replace `runTarget` with the real call into the app.

```ts
import { readFileSync } from 'node:fs';

type Case = { id: string; input: string; expected: { topic: string }; tags: string[] };
type Result = { id: string; score: number; reason: string; tags: string[] };

const THRESHOLD = Number(process.env.EVAL_THRESHOLD ?? 0.8);
const K = Number(process.env.EVAL_TRIALS ?? 1);

async function runTarget(input: string): Promise<{ topic: string }> {
  // Replace with the real target, e.g. `return classifyTicket(input)` imported from src/.
  return { topic: input.toLowerCase().includes('audio') ? 'audio-calidad' : 'ruido' };
}

function grade(output: { topic: string }, expected: { topic: string }): [number, string] {
  const norm = (s: string) => s.trim().toLowerCase();
  return norm(output.topic) === norm(expected.topic)
    ? [1, 'topic matches']
    : [0, `expected "${expected.topic}", got "${output.topic}"`];
}

const cases: Case[] = readFileSync(new URL('./datasets/topic.jsonl', import.meta.url), 'utf8')
  .split('\n').filter((l) => l.trim()).map((l) => JSON.parse(l));

const results: Result[] = [];
let allTrialsPassed = 0;
for (const c of cases) {
  const scores: number[] = [];
  for (let t = 0; t < K; t++) {
    const [score, reason] = grade(await runTarget(c.input), c.expected);
    scores.push(score);
    if (score < 1) console.log(`FAIL ${c.id} trial ${t + 1}: ${reason}`);
  }
  if (scores.every((s) => s === 1)) allTrialsPassed++;
  const mean = scores.reduce((a, b) => a + b, 0) / K;
  results.push({ id: c.id, score: mean, reason: mean === 1 ? 'ok' : 'see failures', tags: c.tags });
}

const score = results.reduce((a, r) => a + r.score, 0) / results.length;
const byTag = new Map<string, number[]>();
for (const r of results) for (const tag of r.tags) byTag.set(tag, [...(byTag.get(tag) ?? []), r.score]);
console.log(`cases=${results.length} trials=${K} score=${score.toFixed(3)} pass^k=${(allTrialsPassed / results.length).toFixed(3)} threshold=${THRESHOLD}`);
for (const [tag, s] of byTag) console.log(`  ${tag}: ${(s.reduce((a, b) => a + b, 0) / s.length).toFixed(3)} (n=${s.length})`);
if (score < THRESHOLD) process.exit(1);
```

`package.json`: `"evals": "tsx evals/run-all.ts"` (a runner that imports each `*.eval.ts`) or,
for a single suite, `"evals": "tsx evals/topic.eval.ts"`. The same file works as a vitest test by
wrapping the loop in `test(...)` and replacing the exit with `expect(score).toBeGreaterThanOrEqual(THRESHOLD)`.

### Pairwise co-grouping (for clustering or triage)

When the target groups items and names groups freely, exact label match is unfair. Score pairs:
for every pair of items that share a group in the ground truth, check whether the target also put
them together. Score = matched pairs / ground-truth pairs (optionally also penalize pairs the
target joined that the truth keeps apart). Pure code, no judge. A low first score (one observed
baseline was 0.208, 54 of 259 pairs) is a baseline, not a verdict: investigate before fixing
(right groups under different names, or invented categories?).

## LLM-as-judge rubric template

```
You are a strict evaluator for <behavior>. You did not produce the answer.
Input: <case input>
Ground truth: <expected>
Answer to grade: <output>

Score from 0 to 1 using these rules, applied in order:
- Start at 1.0.
- Penalty -1.0 (score 0): <critical failure, e.g. states a currency different from the record>.
- Penalty -0.5: <major failure, e.g. omits an item present in the ground truth>.
- Penalty -0.2: <minor failure, e.g. correct facts, wrong format>.
- Floor at 0. Do not reward length, tone or confidence. Ignore the path; grade the final answer.
Return JSON only: {"score": <number>, "reason": "<one sentence naming the penalties applied>"}
```

Explicit penalties matter: a first judge that only described the goal ("check the transfers are
in COP") passed an answer that mixed currencies (a false positive). Rewriting it to penalize any
mention of another currency fixed it. A judge is an external observer; it never changes the
target's output.

Calibration (required before judge scores count toward the gate):
1. A human labels 10 cases (mix of good and bad answers) with a score using the same rubric.
2. Run the judge on the same 10 at temperature 0.
3. Agreement = cases where judge and human land on the same side of the case pass mark. Require
   at least 9/10; otherwise rewrite the rubric (add the penalty the judge missed) and repeat.
4. Record the agreement and the judge model in evals.md. Recalibrate when the judge model changes.

## Thresholds and the regression gate

- Capability evals (while building): the curve rises then flattens. Record each run in the
  history table; the flattening is the signal the feature is ready.
- Regression evals (after release): threshold = baseline minus a tolerance the user approves
  (start with 0.05), never above what the system has demonstrated. `npm run evals` exits non-zero
  below it and runs in CI when the project has CI.
- pass@k (at least one of k trials succeeds) measures capability. pass^k (all k succeed)
  measures consistency. Anything that runs unattended (agents, scheduled jobs, autonomous triage)
  is gated on pass^k with k >= 3.
- Changing a threshold needs the user's OK and a decision-log line with the reason.
- 0% over many trials almost always means the task or grader is broken. Check the grader first.

## Reading transcripts

Before changing a prompt, tool or model: read at least 5 failing transcripts and write one line
each in evals.md (what went wrong, grader right or wrong). Fix the grader when it is wrong; fix
the target when the target is wrong. Never tune the grader toward the current output.

## HITL check for agent tools

For every tool an agent can call, classify: read-only, destructive (delete, overwrite),
irreversible (send email, publish, pay, refund), costly (expensive API, bulk operations).
Destructive, irreversible and costly tools must require approval at the tool level, enforced by
the system before execution (framework approval flag, or a server-side pending-action record the
human approves). A conversational "are you sure?" from the agent is not HITL: nothing stops the
tool from running. Also check that the approval is bound to the arguments (approve "refund 20 to
user A", not "refunds"). A missing gate is a blocker. Agent-wide approval on all tools is allowed
but note the friction on read-only tools.

## Framework notes (brief)

- Mastra: scorers attach to agents or workflows; prebuilt scorers exist (textual, classification,
  prompt) and custom scorers can be code or LLM-judged. Enable observability with sampling 1.0
  while building evals. Tool approval: `requireApproval` on a tool, `requireToolApproval` on an
  agent (check exact names in the installed version's docs). Keep `npm run evals` as the entry
  point even when using Mastra scorers.
- Langfuse, Phoenix (Arize), LangSmith: optional, add dashboards and dataset management at the
  cost of setup. The repo-local `npm run evals` remains the gate.
